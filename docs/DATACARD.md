This card documents two related datasets produced by the same pipeline:

1. **Raw Transaction Dataset** — 10,000 per-user synthetic mobile money transaction CSV files (`data/user_transactions/`) plus a user-level label file (`data/user_labels.csv`), generated by `CalibratedMoMoDataGenerator`.

Both datasets are fully synthetic and calibrated to real Ghanaian mobile money (MTN MoMo) behavioral patterns. No real persons are represented.

## 1. Dataset 1A — Raw Transaction Files

### 1.1 Motivation and Purpose

This dataset was created to enable credit risk model development and research without requiring access to real private financial data. It is calibrated to real Ghanaian mobile money behavioral patterns to maximize ecological validity while preserving full privacy.

The dataset supports multiple modeling paradigms:
- **Static classifiers** (Logistic Regression, XGBoost, Random Forest, LightGBM) — via aggregate features in Dataset 2
- **Sequential models** (Sequential LSTM, Hybrid LSTM) — from per-user transaction sequences, optionally fused with static features
- **Exploratory data analysis** — transaction-level behavioral analysis

### 1.2 Composition

**Scale:** 10,000 users × mean 103 transactions/user = **1,030,696 total transaction rows** across 10,000 CSV files.

Files are named `USER_000000.csv` through `USER_009999.csv` in `data/user_transactions/`.

#### Column Schema

The schema varies by user borrowing status. There are three possible column counts:

**13 core columns** (all users):

| Column | Type | Description | Example |
|---|---|---|---|
| `TRANSACTION DATE` | datetime string | Timestamp with microsecond precision | `2024-01-14 10:30:29.843673` |
| `FROM ACCT` | string | Sender account number | `10425953` |
| `FROM NAME` | string | Sender display name | `User 000000` or `QWIKLOAN_LENDING` |
| `FROM NO.` | string | Sender phone, Ghana E.164 format (`233XXXXXXXXX`) | `233522176667` |
| `TRANS. TYPE` | categorical | One of 8 observed transaction types | `TRANSFER` |
| `AMOUNT` | float | Transaction value (GHS) | `34.95` |
| `FEES` | float | Transaction fee (GHS); `0.0` if none | `0.0` |
| `E-LEVY` | float | Electronic transfer levy (GHS); `0.0` if none | `0.52` |
| `BAL BEFORE` | float | Account balance before transaction (GHS) | `337.76` |
| `BAL AFTER` | float | Account balance after transaction (GHS) | `302.81` |
| `TO NO.` | string | Recipient phone, or `"0"` for service providers | `233485192390` |
| `TO NAME` | string | Recipient name or service provider | `Recipient_00734` |
| `TO ACCT` | string | Recipient account or provider account | `ACCT_36599919` |

**+4 disbursement columns** (borrower files only, on `CREDIT` rows):

| Column | Description |
|---|---|
| `LOAN_PROVIDER` | Lender name (QWIKLOAN, XPRESSLOAN, XTRACASH, FIDO, CEDISPAY) |
| `LOAN_PRINCIPAL` | Loan amount disbursed (GHS) |
| `LOAN_INTEREST_RATE` | Fixed at `0.069` (6.9%) |
| `LOAN_DUE_DATE` | Repayment due date string (`YYYY-MM-DD`) |

**+2 repayment columns** (borrower files with repayments, on `LOAN_REPAYMENT` rows):

| Column | Description |
|---|---|
| `LOAN_PRINCIPAL_PAID` | Principal component of repayment (GHS) |
| `LOAN_INTEREST_PAID` | Interest component of repayment (GHS) |

> ⚠️ **Variable schema:** Non-borrower files have **13 columns**. Files with only loan disbursements have **17 columns**. Files with repayments have **19 columns**. Parsers must handle these variations. Use `pd.read_csv(..., low_memory=False)` and check column presence before accessing loan fields.

### 1.3 Transaction Types

Eight transaction types are observed in the data. The ninth type (`ADJUSTMENT`) is defined in the feature engineering code but is **never generated**.

| Type | Semantic | Observed % (200-user sample) | Calibration target |
|---|---|---|---|
| `TRANSFER` | Peer-to-peer money transfer | 45.1% | 52.9% |
| `DEBIT` | Merchant payment / bill deduction | 23.1% | 27.2% |
| `CASH_IN` | Mobile wallet top-up (inflow) | 12.1% | — (added on top) |
| `PAYMENT` | Service/utility payment | 6.3% | 4.1% |
| `PAYMENT_SEND` | Payment sent to another party | 6.2% | 10.8% |
| `CASH_OUT` | Cash withdrawal | 4.4% | 5.0% |
| `CREDIT` | Loan disbursement (inflow from lender) | 1.5% | — (loan) |
| `LOAN_REPAYMENT` | Loan repayment (outflow to lender) | 1.4% | — (loan) |
| `ADJUSTMENT` | System correction | **0%** (never generated) | — |

**Note on calibration drift:** Observed percentages differ from calibration targets because `CASH_IN` and loan types are injected on top of the five base types rather than drawn from the same distribution. The generator normalizes only among {TRANSFER, DEBIT, PAYMENT, PAYMENT_SEND, CASH_OUT}.

### 1.4 Temporal Coverage

| Property | Value |
|---|---|
| Observation window | 2024-01-01 to 2024-06-30 (180 days) |
| Account start offset | Uniform(0, 14) days after 2024-01-01 per user |
| Mean transactions per user | 103.1 (std 10.4, min 66, max 144) |
| Inter-arrival distribution | Gamma(shape=2, scale=~10 hours mean) |
| Weekend transaction rate | 30.2% (calibration target: 32.2%) |
| Night transaction rate (22:00+) | 7.9% (calibration target: 8.1%) |
| Early morning rate (<06:00) | varies per user preference |

Weekend inter-arrival times are compressed by a ×0.7 multiplier. Night-hour transactions use a preferred hour drawn from Beta-distributed user preference.

### 1.5 Amount and Fee Distribution

**Amount generation:**

| Parameter | Value | Source |
|---|---|---|
| Base distribution | Lognormal(μ=2.84, σ=1.00) | `data/synthetic_params.json` |
| Mean amount (GHS) | 32.80 | `synthetic_params.json` |
| Median amount (GHS) | 18.50 | `synthetic_params.json` |
| Per-user μ perturbation | Normal(2.84, 0.2) | `generate_user_profile()` |
| Per-user σ perturbation | max(0.5, Normal(1.00, 0.1)) | `generate_user_profile()` |

**Per-type amount multipliers** (applied to base lognormal draw):

| Type | Multiplier |
|---|---|
| CASH_OUT | ×1.81 |
| CASH_IN | ×1.20 |
| TRANSFER | ×1.00 |
| PAYMENT_SEND | ×0.63 |
| DEBIT | ×0.55 |
| PAYMENT | ×0.44 |

**Fee and e-levy logic:**
- `fee_rate = 0.243` — 24.3% of users accept fees (per `synthetic_params.json`)
- CASH_OUT and PAYMENT_SEND: 50% chance of fee = `min(amount × 0.01, 5.0)` (floor GHS 0.25)
- E-levy (1.5%): applied to TRANSFER/PAYMENT_SEND/CASH_OUT > GHS 100 with 30% probability

### 1.6 Balance Dynamics

| Property | Value |
|---|---|
| Initial balance distribution | max(50, Normal(305.88, 151.28)) GHS |
| Calibration mean balance | GHS 305.88 (`synthetic_params.json`) |
| Calibration balance std | GHS 302.55 (halved to GHS 151.28 in generator) |
| Minimum balance threshold | Uniform(10, 100) GHS per user |
| Balance enforcement | CASH_IN forced when balance < threshold |
| Low balance rate | 1.9% of transactions (`synthetic_params.json`) |

## 2. Dataset 1B — User Labels (`data/user_labels.csv`)

### 2.1 Schema

| Column | Type | Description |
|---|---|---|
| `user_id` | string | `USER_000000` through `USER_009999` |
| `credit_archetype` | categorical | One of 5 behavioral archetypes (see §2.2) |
| `loans_taken` | int | Number of loan disbursements during simulation (0–6) |
| `credit_risk_label` | int | Credit risk label: -1, 0, 1, or 2 (see §2.3) |
| `final_credit_limit` | float | Credit limit at end of simulation (GHS) |
| `gen_txn_count` | int | Total transactions generated for this user |

### 2.2 Credit Archetype Distribution

Five behavioral archetypes control transaction frequency, type mix, loan behavior, and repayment likelihood.

| Archetype | Count | Actual % | Target % | Description |
|---|---|---|---|---|
| `non_borrower` | 4,025 | 40.25% | 40% | Never takes loans |
| `responsible_borrower` | 3,542 | 35.42% | 35% | Regular, on-time repayment |
| `occasional_borrower` | 1,479 | 14.79% | 15% | Infrequent loans, variable timing |
| `risky_borrower` | 746 | 7.46% | 8% | Frequent loans, 15% default probability |
| `defaulter` | 208 | 2.08% | 2% | 100% default probability |

### 2.3 Credit Risk Label Distribution

| Label | Meaning | Count | % of all users | % of borrowers only |
|---|---|---|---|---|
| `-1` | No loans taken | 4,025 | 40.25% | — |
| `0` | Good — all loans repaid on time | 3,325 | 33.25% | 55.7% |
| `1` | Late — at least one loan repaid after 30-day term | 1,984 | 19.84% | 33.2% |
| `2` | Default — at least one loan not repaid | 666 | 6.66% | 11.1% |

**Label assignment rule:** A user's final label is the worst-case label across all loans they took (`max` of per-loan outcomes).

**Binary target used in model training:** `default = (credit_risk_label == 2)` → **666 positives out of 5,975 borrowers ≈ 11.1% default rate** (~8:1 class imbalance).

Non-borrowers (`credit_risk_label == -1`) are **excluded from all model training** but are present in this file.

### 2.4 Loan Parameters

All loan parameters are fixed constants applied uniformly across all archetypes (eligibility and repayment timing vary by archetype).

| Parameter | Value |
|---|---|
| Minimum loan amount | GHS 25 |
| Maximum loan amount | GHS 1,000 |
| Annual interest rate | 6.9% |
| Penalty rate | 12.5% |
| Loan term | 30 days |
| Initial credit limit | GHS 50 |
| Credit limit growth per on-time repayment | ×1.25 |
| Maximum credit limit | GHS 1,000 |
| Minimum account age for eligibility | 90 days |
| Minimum transaction count for eligibility | 15 transactions |

**Observed final credit limit stats (GHS):** mean 46.88, std 42.56, min 0, median 50, max 122.07.

Loan providers: QWIKLOAN, XPRESSLOAN, XTRACASH, FIDO, CEDISPAY (assigned per-user at profile generation time).

## 3. Dataset 2 — Engineered Feature Dataset (`data/user_features.csv`)

### 3.1 Motivation and Purpose

This dataset collapses each user's per-transaction history into 29 scalar aggregate features suitable for static classifiers (Logistic Regression, XGBoost). It is produced by `TemporalTransactionFeatureEngineer.create_user_level_summary()` via the standalone `build_user_feature_dataset()` function.

**Important:** This file does **not** contain loan-specific signals. Nine additional loan features are computed at model training time by `CreditRiskDataLoader._engineer_loan_features()` directly from the raw transaction CSVs — see §3.4.

### 3.2 User-Level Feature Schema (29 features)

The file has 30 columns: `user_id` + 29 features.

**Transaction volume and amount (8 features):**

| Feature | Description |
|---|---|
| `obs_txn_count` | Total transactions in the user's CSV |
| `total_volume` | Sum of all AMOUNT values (GHS) |
| `avg_transaction_amount` | Mean AMOUNT (GHS) |
| `median_transaction_amount` | Median AMOUNT (GHS) |
| `std_transaction_amount` | Standard deviation of AMOUNT |
| `max_transaction_amount` | Largest single transaction (GHS) |
| `min_transaction_amount` | Smallest single transaction (GHS) |
| `cv_transaction_amount` | Coefficient of variation (std / mean) |

**Transaction type mix (4 features):**

| Feature | Description |
|---|---|
| `pct_transfers` | Fraction of transactions that are TRANSFER |
| `pct_debits` | Fraction that are DEBIT |
| `pct_cashouts` | Fraction that are CASH_OUT |
| `pct_payments` | Fraction that are PAYMENT or PAYMENT_SEND |

**Temporal behaviour (4 features):**

| Feature | Description |
|---|---|
| `avg_hours_between_txns` | Mean inter-transaction interval (hours) |
| `pct_weekend_txns` | Fraction of transactions on weekends |
| `pct_night_txns` | Fraction at hour ≥ 22 |
| `pct_early_morning_txns` | Fraction at hour < 6 |

**Balance statistics (5 features):**

| Feature | Description |
|---|---|
| `avg_balance` | Mean BAL BEFORE (GHS) |
| `min_balance` | Minimum BAL BEFORE (GHS) |
| `max_balance` | Maximum BAL BEFORE (GHS) |

| `pct_low_balance_txns` | Fraction of transactions where BAL BEFORE < GHS 20 |

**Fee behaviour (3 features):**

| Feature | Description |
|---|---|
| `total_fees_paid` | Total FEES + E-LEVY paid (GHS) |
| `avg_fees_per_txn` | Mean fees per transaction (GHS) |
| `pct_txns_with_fees` | Fraction of transactions with FEES > 0 |

**Recipient and diversity (3 features):**

| Feature | Description |
|---|---|
| `unique_recipients` | Number of distinct TO NAME values |
| `recipient_concentration` | Fraction of transactions going to single most frequent recipient |
| `unique_txn_types` | Number of distinct TRANS. TYPE values used |

**Activity span (2 features):**

| Feature | Description |
|---|---|
| `account_age_days` | Days between first and last transaction |
| `transactions_per_day` | obs_txn_count / max(account_age_days, 1) |

### 3.4 Loan Features Computed at Training Time

Nine additional features are computed by `CreditRiskDataLoader._engineer_loan_features()` at model training time. They are **not stored in `user_features.csv`** but are appended to the static feature matrix before fitting.

| Feature | Description |
|---|---|
| `total_loan_volume` | Sum of all CREDIT amounts (GHS) |
| `avg_loan_amount` | Mean loan disbursement (GHS) |
| `max_loan_amount` | Largest single loan (GHS) |
| `loan_to_total_volume_ratio` | total_loan_volume / total transaction volume |
| `pct_credit_transactions` | Fraction of transactions that are CREDIT |
| `loan_timing_in_sequence` | Position of first CREDIT transaction (0 = early, 1 = late) |

| `balance_to_loan_ratio_at_disbursement` | avg_balance_at_loan / avg_loan_amount |

All 9 features are set to `0` for non-borrowers.

### 3.5 Transaction-Level Feature Space (LSTM Inputs)

Transaction-level features are an intermediate product produced by `extract_all_features()`. They are not persisted to disk as a standalone file but are used directly by `CreditRiskDataLoader.load_sequences()` to build LSTM inputs, which are cached to `data/lstm_sequences.npz`.

**113 transaction-level features** are extracted, grouped into 11 categories:

| Category | Count | Example features |
|---|---|---|
| Amount transforms | 3 | `log_amount`, `sqrt_amount`, `amount_squared` |
| Amount size bins | 4 | `is_micro_txn` (<10), `is_small_txn` (10–50), `is_medium_txn` (50–200), `is_large_txn` (200+) |
| Fee features | 5 | `has_fees`, `has_elevy`, `total_cost`, `fee_to_amount_ratio`, `elevy_to_amount_ratio` |
| Transaction type one-hots | 7 | `is_transfer`, `is_debit`, `is_payment`, `is_payment_send`, `is_cash_out`, `is_cash_in`, `is_adjustment` |
| Temporal features | 13 | `hour`, `day_of_week`, `is_weekend`, `hour_sin`, `hour_cos`, `day_sin`, `day_cos`, time-of-day bins |
| Balance dynamics | 10 | `log_balance_before`, `balance_change`, `balance_pct_change`, `is_low_balance`, `will_deplete_balance` |
| Sequence position / cumulative | 6 | `time_since_last_txn_hours`, `txn_number`, `cumulative_volume`, `cumulative_fees_paid` |
| Count-based rolling windows (n=3,5,10) | 24 | `last_{n}_avg_amount`, `last_{n}_std_amount`, `last_{n}_transfer_count` |
| Time-based rolling windows (3d,7d,14d,30d) | 28 | `rolling_{w}_count`, `rolling_{w}_sum`, `rolling_{w}_balance_volatility` |
| Behavioural patterns | 4 | `unique_recipients_so_far`, `unique_txn_types_last_10`, `is_repeated_recipient` |
| Risk indicators | 8 | `unusual_hour`, `rapid_transaction`, `rapid_balance_drop`, `consecutive_withdrawals`, `risk_score` |

**LSTM subset:** 38 of the 113 features are selected (`LSTM_FEATURE_COLUMNS` in `credit_model.py`). Sequences are pre-padded with zeros to `max_seq_len=50`. A Keras `Masking(mask_value=0.0)` layer ignores the padding during training.

## 4. Data Generation Process

### 4.1 Generator

**Class:** `CalibratedMoMoDataGenerator` in `src/seqcredit_model/synthetic_data.py`
**Entry point:** `python src/seqcredit_model/synthetic_data.py`

**Key generation parameters:**

| Parameter | Value |
|---|---|
| Number of users | 10,000 |
| Average transactions per user | 100 (Poisson-distributed) |
| Simulation start date | 2024-01-01 |
| Simulation duration | 180 days |
| Recipient pool size | 1,000 reusable synthetic recipients |

### 4.2 Calibration

The generator reads `data/synthetic_params.json`, which contains 12 parameters derived from real Ghanaian mobile money (MTN MoMo) data:

```json
{
  "amount_lognormal_mu": 2.84,
  "amount_lognormal_sigma": 1.00,
  "amount_mean": 32.80,
  "amount_median": 18.50,
  "transaction_frequency_hours": -10.01,
  "balance_mean": 305.88,
  "balance_std": 302.55,
  "type_distribution": {
    "TRANSFER": 0.529, "DEBIT": 0.272, "PAYMENT_SEND": 0.108,
    "CASH_OUT": 0.050, "PAYMENT": 0.041
  },
  "weekend_rate": 0.322,
  "night_rate": 0.081,
  "fee_rate": 0.243,
  "elevy_rate": 0.127,
  "self_transfer_rate": 0.0,
  "low_balance_rate": 0.019
}
```

> ⚠️ **Calibration provenance gap:** The source dataset used to derive these parameters, its collection date, collection method, and consent process are not documented in this repository.

### 4.3 Reproducibility

> ⚠️ **No random seed:** `synthetic_data.py` does not call `numpy.random.seed()` before generation. Each run of `generate_dataset()` will produce a statistically similar but numerically different dataset. Exact reproduction of the committed `user_labels.csv` is not possible from code alone.

The feature engineering pipeline and model training use `set_random_seeds(42)` (from `src/seqcredit_model/credit_model.py`) for reproducibility after data is generated.

## 5. Preprocessing and Transformations

### Raw Transaction Data
- Transactions are sorted by `TRANSACTION DATE` within each user file during feature extraction
- Timestamps are parsed with `pd.to_datetime()`
- No outlier removal, capping, or imputation is applied to raw data
- All rows are included in feature aggregation

### Static Feature Pipeline (Logistic Regression / XGBoost)
- `StandardScaler` is fitted on training features only (test set is transformed, not fitted)
- Non-borrowers (`credit_risk_label == -1`) are dropped before splitting
- 9 loan features are appended after scaling

### LSTM Sequence Pipeline
- `StandardScaler` is fitted on flattened training sequences only
- `NaN` and `Inf` values are replaced with `0.0` via `np.nan_to_num()`
- Sequences are pre-padded with zeros on the left to `max_seq_len=50`
- A `Masking(mask_value=0.0)` layer ignores padded timesteps during training
- Preprocessed sequences are cached to `data/lstm_sequences.npz` after first load

### Train/Test Split
- Stratified 80/20 split on `user_id` (stratified by binary default label)
- `prepare_static_splits()` **must be called before** `load_sequences()` so all three models share the same train/test user IDs

## 6. Intended Uses

### Intended
- Research and education on credit risk modeling with mobile money data
- Benchmarking static vs. sequential modeling architectures
- Developing and testing feature engineering pipelines for financial time-series
- Teaching end-to-end data science workflows in a financial inclusion context

### Out of Scope
- **Must not** be used for actual credit decisions — the data is synthetic and reflects generator assumptions, not real borrower behavior
- **Must not** be represented as a dataset of real Ghanaian users or real MoMo transaction records
- The loan parameters (6.9% interest, 12.5% penalty) are simulation parameters only and do not represent any regulated financial product

## 8. Maintenance and Reproducibility

**Maintained by:** Benjamin Ekow Attabra (`attabeezy` on GitHub)

**Regeneration order is strict:** `synthetic_data.py` must run before `feature_engineering.py`. `user_features.csv` and `user_labels.csv` must come from the same generation run.

**Stale-file detection:** `CreditRiskDataLoader._validate_data()` cross-checks `obs_txn_count` (from `user_features.csv`) against `gen_txn_count` (from `user_labels.csv`) for a random sample of 20 users. A mismatch prints a warning. The committed files have a 0% match rate (obs mean 17.4 vs gen mean 103.1), which will trigger this warning on every training run.

**LSTM cache invalidation:** If `user_transactions/` is regenerated, delete `data/lstm_sequences.npz` before retraining to force a cache rebuild.

## 9. Ethical Considerations

- All data is **fully synthetic**; no real persons, accounts, or phone numbers are represented
- Phone numbers are random integers conforming to Ghana's E.164 format (`233XXXXXXXXX`); names are `User_XXXXXX` or `Recipient_NNNNN`
- The credit archetype distribution (2% defaulters, 8% risky borrowers) is a modeling choice. Models trained on this data will reflect the generator's distributional assumptions
- The calibration to "real Ghanaian mobile money patterns" is asserted but the provenance of `synthetic_params.json` is undocumented — the origin, collection method, and any consent process for the source data are unknown
- If adapted for real deployment, false positive and false negative errors in credit scoring have **asymmetric harms**: false negatives (missed defaults) expose lenders to loss; false positives (denied credit) exclude creditworthy borrowers, which is a particular concern in financial inclusion contexts

## 10. Known Limitations and Data Quality Notes

| # | Limitation | Impact | Source |
|---|---|---|---|
| 1 | **`user_features.csv` is stale** — generated from a different run (obs mean 17 txns vs current 103 txns). 0% of users match within 5%. | High — any model using this file is trained on mismatched features | Cross-referencing `obs_txn_count` vs `gen_txn_count` |
| 2 | **No random seed in `synthetic_data.py`** — `generate_dataset()` is not deterministic | Medium — exact reproduction impossible; statistical properties are consistent | No `np.random.seed()` call in `synthetic_data.py` |
| 3 | **`ADJUSTMENT` type never generated** — `is_adjustment` feature is always 0 | Low — column is defined but uninformative | `_select_transaction_type()` excludes ADJUSTMENT from sampling |
| 4 | **Variable file schema** (13, 17, or 19 columns) — non-borrower, disbursement-only, and repayment files differ | Medium — generic CSV parsers must handle optional columns | Comparing non-borrower and borrower CSV files |
| 5 | **Calibration source undocumented** — `synthetic_params.json` provenance not recorded | Medium — limits ability to assess real-world generalizability | No source attribution in codebase |
| 6 | **Binary collapse of 4-class label** — labels 0 and 1 (good and late) are merged as "non-default" | Medium — late-payer subgroup is not separately modeled | `credit_model.py` `load_static_data()` target definition |
| 7 | **8:1 class imbalance** among borrowers (11.1% default rate) | Medium — requires `class_weight='balanced'` or `scale_pos_weight` (both implemented) | Label distribution |
| 8 | **`account_age_days` is implausibly short in current `user_features.csv`** (mean 5 days) due to the stale file — current transaction files span up to 180 days | High (part of limitation #1) | Comparing stale stats to current transaction dates |
